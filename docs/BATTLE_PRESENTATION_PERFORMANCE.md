# 戦闘表示の負荷調査

## QQ-0.56.7 / 2026-10-28

毎フレーム、両者のカードについて通常・詳細のツールチップを再構築し、詳細表示ではGrade 0〜5の効果量まで再計算していました。カードの枠のStyleBox、効果チップのレイアウト、名前の文字幅計測も繰り返していました。また、上部バナーでは遺物の全Controlを毎フレーム削除・生成していました。

変更内容:

- カードの表示値と比較値をスナップショットし、変更時のみツールチップ・効果表示を作成する。定義のインスタンスが同じでも、入れ子の効果量が変われば無効化する。
- 枠色・太さが変わらなければStyleBoxを再利用する。名前の変更・リサイズ時は文字幅を再計算する。
- 遺物のControlを再利用し、内容・言語・刻印カードなどの変更は反映する。
- 戦闘ログは内容が変わった場合のみ結合する。同じ件数の置き換え・削除にも対応する。
- 戦闘シミュレーション、通信、タイムライン座標、秒数、HPアニメーション、演出の頻度は変更しない。

Windows / Godot 4.6.2 headless、同じbalanced対scout、ウォームアップ5フレーム後の90回を比較。時間を止めたUI更新のCPU時間であり、実際のFPSやGPU時間ではありません。各UI全体の更新後、同じフレームで個別コンポーネントも計測する固定治具です。

| --- | ---: | ---: | ---: | ---: |
| 0 | 13.320ms | 1.585ms | 16.448ms | 2.166ms |
| 30 | 14.705ms | 1.769ms | 17.523ms | 2.549ms |

同条件でUI更新の平均CPU時間は約88%減りました。手札単体は約7.4〜7.6msから約0.6〜0.8ms、遺物30個のバナーは約1.86msから約0.14msになりました。個別の数値は測定環境・実行時負荷で変動します。

## ブラウザ確認

ローカルのWeb Layout ReviewビルドをChrome headlessで実行し、遺物30個・高HPで両者のカードを使用する戦闘を各8秒計測しました。1440x900で727フレーム、960x600で837フレーム。UI更新P95はそれぞれ3.4ms・3.2ms、画面全体のフレーム間隔P95は13.3ms・11.5msでした。スクリプトエラーはありませんでした。

一方、画面全体の最大間隔には204.3ms・61.9msのスパイクが残りました。今回のCPU最適化だけで全てのカクつきが解消したとは判断していません。GPU・ブラウザ・初回描画などの残る要因は別途切り分けが必要です。

ブラウザ検証: `tools/build_web_layout_review.ps1` 後に `node tools/web_battle_performance_review.mjs`。結果と画像は `tools/.local/battle-stutter/browser/` に保存します。

## ゲーム内の計測

開発者モードの戦闘パネルから「戦闘負荷を計測（5秒）」を押します。通常プレイ中はサンプリングせず、押した場合のみ最大2400フレームを収集します。実時間のフレーム間隔、UI更新時間、33msを超えたフレーム数を表示します。サーバーへの送信やセーブの変更はありません。

UI更新時間は `_refresh_ui` のCPU時間です。画面全体のフレーム間隔には描画や待ち時間も含まれ、両者は別の指標です。平均だけでなくP95・最大値を比較してください。

回帰テスト: `tests/BattlePresentationPerformanceSmoke.tscn`。表示キャッシュの再利用・変更時の無効化・全カードのGrade 0/3/5・補正色・言語・遺物・ログ・任意計測を検証します。
