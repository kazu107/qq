# 無限ランキングと開発者権限

## プレイと表示

- ハブの「無限ランキング」から閲覧します。閲覧はログイン不要です。
- 「ランキングに挑戦」は、ユーザー名登録済みのアカウントでWeb版にログインすると使えます。通常の無限モードとは別の挑戦です。
- 永続強化を適用せず、全7デッキ・全カード・全遺物を共通条件で使います。通常無限と同じ初期無限補正は適用します。
- 既存の無限スコア規則を使用します。サーバーで再計算した正式記録だけを、1アカウントにつき各条件の自己ベスト1件で掲載します。同点は同順位です。表示順は達成日時・記録IDで固定します。
- シーズンは`season-1`からの番号制です。月替わりでは終了せず、無限モードの内容を変更したときに次のシーズンを開始します。シーズンと開始デッキで絞り込み、自分の順位、挑戦履歴、最終カード・遺物、スコア内訳を確認できます。
- ルール選択やルール別集計はありません。自己ベストと順位はシーズン・開始デッキの条件ごとです。内部の検証互換性番号は1シーズンに1つ固定し、更新前後のスコアは別シーズンに残します。
- 通常・アリーナとは別の`ranked`中断枠に保存します。戦闘途中も入力記録から再構築します。「ランキングの続き」で復元できます。
- 戦闘の敗北時に自動送信します。ハブの「挑戦を終了・送信」では、戦闘外ならその時点の記録を確定できます。
- 通信が切れたときは送信待ち記録を保持し、同じアカウントでログインすると再送します。再開時には接続と所有者を確認し、サーバーが受領した記録との食い違いを修復してから再実行します。GoogleとGitHubは別アカウントのままなので、所有アカウントを切り替えて投稿できません。
- 終了済みの送信待ちは別の永続送信キューにも保持します。次のランを始めたり設定を初期化しても消えず、ウィンドウを閉じた後も再送します。
- 古い通常無限セーブや導入前のランは、初期状態から記録されていないため投稿できません。

## 検証の仕組み

1. サーバーがアカウント、開始デッキ、ランID、seed、シーズン、ルール版を固定します。
2. クライアントはマップ選択・購入・報酬・装備・戦闘操作を記録します。戦闘は固定1/60秒刻みで、何も操作していない区間はtick数として圧縮します。
3. 操作番号ごとにPostgreSQLへ追記します。同じ内容の再送は許可し、書き換え・飛び番号・別アカウントからの操作は拒否します。
4. 終了後、Nodeサーバーとは別のネイティブGodotプロセスで同じゲームロジックを再実行します。報酬・イベント・鍛冶などの乱数も、記録上の操作順とseedから再現します。
5. クライアント申告のスコアや勝敗は採用せず、再実行から算出したスコアだけを正式記録にします。

開発者操作や不正な操作順、未完了の戦闘は対象外です。シーズン終了までにサーバーへ確定した記録だけを対象にします。
署名やクライアントの「開発者モード未使用」という自己申告だけには依存しません。ブラウザ表示を改造できても、サーバー上の正当な進行なしに得点は増えません。
自動操作するbotそのものを完全に判別する機能ではありません。

## サーバー設定

既存のOAuth・PostgreSQLをそのまま使います。追加の有料サービスや別dynoを自動契約・起動する処理はありません。

| 変数 | 用途 |
| --- | --- |
| `DEVELOPER_USERNAMES` | Web開発者モードを許可するユーザー名。カンマ区切り。例: `kazu107,uttu03` |
| `DEVELOPER_USER_IDS` | UUIDによる追加許可。未設定でも可 |
| `RANKED_VERIFIER_ENABLED` | `true`で検証キューを処理。無効時は待機中となり、正式ランキングへは掲載しません |
| `GODOT_VERIFIER_PATH` | ローカル検証時のGodot実行ファイル。Herokuは自動配置されたLinux版を使用 |

Herokuビルド時の`heroku-postbuild`がGodot 4.6.2公式Linuxランタイムを取得し、GitHub公式のSHA-256ダイジェストと照合します。
検証用PCKは既存のR2配信を再利用し、manifestのルール版、URL、容量とSHA-256を確認してRAM/一時ディスクをキャッシュします。
重い検証は別プロセス・同時1件で実行し、既存のHTTP・WebRTCシグナリングのイベントループでは直接ゲームを実行しません。
子プロセスへOAuth SecretやDB接続情報を渡さず、セーブ先も専用一時フォルダへ隔離します。

検証上限は1ラン20万操作・2千万tick・1回120秒です。予算超過・ランタイム障害で判定できない記録を、正当な記録として扱うことはありません。
長時間の無限ランで上限に達した場合は`unverified`などで理由を表示します。運用状況に応じて分割検証や専用workerへ拡張してください。
キューはDBに保存するためdyno再起動で消えず、処理中のリースが切れた記録は再試行できます。
終了リクエストで検証処理を起動し、キューが空ならDBの定期ポーリングを停止します。アイドル中にDBを常時起こし続ける方式ではありません。
起動時には実際のランタイムとPCKで、DBへ記録を作らない初期状態の自己テストを行い、成功すると`RANKED_VERIFIER_READY`をログへ出します。

## ルールを更新するとき

無限モードのバランス、得点、敵数、進行、カード・遺物効果などを変更した場合は、`RankedSession.RULESET`と`server/ranking/rules.json`の`infinite-N`を一緒に増やします。R2 manifestの`ranking_ruleset`は同じJSONから生成します。内部番号を使うのは再生検証と更新検出だけで、ユーザーに切り替えは表示しません。
公開サーバーのリリース処理で、旧シーズンの終了時刻と新シーズンの開始時刻を同じ時刻に確定します。DBロックで同時作成を防ぎ、同じ内部番号の再起動や月替わりでは増やしません。古い番号のサーバーは新しいシーズンを巻き戻せません。UIのみの変更は内部番号を更新せず、シーズンを継続します。今後の実装時の必須手順はルートの`AGENTS.md`にも記載しています。

## 旧テスト記録の削除

`node tools/ranking_maintenance.mjs inspect`はHeroku上で件数と対象を確認します。
`node tools/ranking_maintenance.mjs backup-and-delete <run-id> <score>`は旧形式の正式記録が全体で1件であること、指定ID・点数・状態を照合し、操作記録を含む退避データを`tools/.local/ranking-reset/`へ保存してから削除します。退避内容のハッシュを再照合し、異なる対象・増えた正式記録・変更済みデータがあれば中止します。削除するのは指定のテスト記録とその操作ログ、および参照のない旧シーズンだけです。アカウントやセーブは変更しません。本番DBをテスト用DBとして使わず、削除処理の検証は使い捨てPostgreSQLで行います。

## 開発者モード

サーバーは有効なセッションの登録済みユーザーに対してだけ`canDeveloper`を返します。許可リストはPCKやゲーム内設定ではなくHeroku側で管理します。
未ログイン・許可されていないユーザーは、古いセーブに開発者モードONが残っていても切り替えを表示せず、有効にもなりません。
ログアウト時や権限を失ったときも非表示にします。エディタと専用QAエクスポートは開発のため引き続き利用可能です。
これはローカル表示・ツールの制限であり、ユーザーが改造したブラウザ全体を信頼する仕組みではありません。ランキングの検証は別途サーバーで強制します。

## テスト

- `npm test`: 認証・権限、所有者照合、CSRF、再送、シーズン締切、自己ベスト・同順位、スコアの直接申告が採用されないことを検証します。
- 実DBテストは`QQ_AUTH_TEST_DATABASE_URL`で指定した、ループバック上の使い捨て`qq_auth_tests`だけを初期化します。本番DBでは実行しません。
- `RankedRunSmoke`: 戦闘途中の中断・復元、入力記録の再実行による同スコア、開発者コマンドの拒否を検証します。
- CIではLinux版Godotでも同じテストを実行し、Web用に出力したPCKをネイティブGodotで読み込んで再実行できることを検証してから配信します。
